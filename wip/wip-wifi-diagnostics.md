# Diagnostics over Wi-Fi

Status: Implement (steps 1-12 done; only the user hardware check, step 13, remains)

## Description
Review the device's status and recent logs over Wi-Fi: a simple diagnostics web page, or just plain HTTP endpoints
that `curl`/`wget` can fetch. Nothing fancy.

The irtx project (`C:\Users\Brad\Projects\irtx`) had serial, telnet, a web page and an embedded web terminal; that
was more than needed and made things messy. Keep this small.

## Notes
- **irtx (Arduino):** own `LOG`/`PRINT`/`VERBOSE` macros (`config.h`) fanned out by `logWrite` to every `Console` subclass (serial, telnet `telnet.cpp`, websocket `ws.cpp`) plus a "dmesg" ring; `CaptureConsole` captured command output for HTTP. `http.cpp` (Arduino WebServer): `/api/status`, `/api/dmesg`, `/api/command` (POST, runs console commands), `/api/upload`, `/api/reload-activities`, static web files. **Reuse:** the dmesg ring idea and `/api/status` + `/api/dmesg` shape. **Mess:** several console transports, a command shell over every channel, own log macros parallel to the platform's, web terminal and file upload. None of its code is portable (Arduino `String`, WebServer).
- **Capture logs here:** keep `ESP_LOGx`; hook `esp_log_set_vprintf()` with a wrapper that `vsnprintf`s into a small stack/static line buffer, appends to the ring, then calls the previous vprintf (UART unchanged). Must be non-blocking (spinlock from `port.h`, no mutex wait; drop on contention) as logs come from any task. Not ISR (ESP_EARLY_LOG / ISR logs bypass vprintf).
- **Ring in PSRAM:** log writes are ~100 bytes per line, a few lines/s: negligible against the fill (rule targets bulk writers like page builds). Could also stay internal if small (8-16 KB), but internal RAM is tight (~106 KB free connected), so PSRAM, e.g. 32-64 KB. Pure, host-testable: ring (append, wrap, read from sequence number `since`, line-aligned eviction) and JSON/text formatting of a status struct.
- **esp_http_server (IDF v6.0):** one task (`httpd_config_t.stack_size` default 4096, `task_priority` 5, `core_id` tskNO_AFFINITY), `max_open_sockets` default 7 (each a lwIP socket; LWIP_MAX_SOCKETS default 10, net_worker also uses sockets), ~ a few KB extra per session. Suggest: stack ~4-6 KB (JSON built into a stack/PSRAM buffer, chunked responses `httpd_resp_send_chunk`), `max_open_sockets` 2-3, core 0, priority low (below protocol/op tasks, e.g. 2), `lru_purge_enable`. Expect ~8-12 KB internal total; measure.
- **Status sources:** `main.cpp` once-a-second stats (FPS, fill time, late fills from `screen.cpp`, compositor, images); heap (`heap_caps_get_free_size` internal/PSRAM, largest block, min free); `wifi.cpp` `WifiStatus` snapshot (state, reason, ip; rssi/mac live, `wifi_get_status`-style used by `protocol.cpp:722`); net counters (`CB_STATS_LOG` path in net_worker); op queue / script stats (`standalone_task.cpp` logs); layout summary (`layout_summary()` in `layout_boot`); clock/NTP (`wifi.cpp` `s_sntp_on`, sync state); uptime (`esp_timer_get_time`); versions (`esp_app_get_description()`: app version, IDF version, build date). Several of these are only logged, not stored: will need small getters.
- **Hostname:** `wifi.cpp:169` sets DHCP hostname `controlblock-xxxxxx` (last 3 MAC bytes). **No mDNS** (no `espressif/mdns` in `idf_component.yml`); adding it costs a component + RAM; DHCP hostname often resolves on home routers anyway.
- **Security:** LAN only, read-only GETs, no command/upload endpoint. Logs may leak SSID/IPs/URLs from layout ops; passwords are not logged (check). Optional NVS toggle (set via `cli wifi`) to disable.
- **Suggested endpoints:** `GET /status` (JSON), `GET /log` (text, whole ring), `GET /log?since=N` (lines after sequence N; response header `X-Log-Next`) for polling tail via `curl`/a tiny script; optional `GET /` minimal HTML page that polls both.

## Flagged assumptions
- Step 8: mDNS and the server go up on every connect and down on every disconnect (`mdns_free`), rather than staying up across reconnects.
- Step 8: a rename applies to mDNS immediately, to the DHCP hostname on the next lease (not forced).
- Step 9: `/log` allocates the 32 KB PSRAM scratch per request rather than keeping it resident.
- PSRAM ring of 32 KB is fine for the fill (small writes); verify with a `RUN_STRESS` run while logging.
- Server task on core 0 at low priority; heavy JSON built off the internal heap.
- No mDNS initially; rely on IP shown/logged and DHCP hostname.
- Step 2: the ring lock is a try-flag, and `log_capture_read` copies the ring under it, so lines logged during a read are dropped from the ring (UART unaffected). Fine for a few lines/s.
- Step 3: `DiagStatus` fields guessed ahead of step 4 (compositor builds/avg, image count/bytes, net requests/errors/dropped, ops busy + script stats, layout loaded/activities/activity/summary); step 4 may adjust them to what the getters really have.
- Step 4: the screen and compositor stats getter lives in `diag_collect` (sampled by main once a second) rather than in `screen.cpp`, since those stats reset on read; `/status` values are up to a second old. `diag_collect` reads the device name and Wi-Fi/standalone copies without locks (torn reads cosmetic).
- Step 5: `NAME_SET` with the default name spelled out stores it (pinned: no longer follows the MAC); empty goes back to following the MAC. `DeviceName` lives in `wifi.cpp` (it needs the MAC; loaded in `wifi_init`, before `host_link_init`).
- Step 6: message types `NAME_SET` 0x60 / `NAME_GET` 0x61 (a new 0x6x group) rather than a Wi-Fi field.
- Step 7: the CLI is its own `name` command (`name [get]`, `name set <name>|--default`), like `time`, not a `wifi` option.

## Decisions (user, 2026-11-09)
1. **Endpoints plus a tiny page:** `GET /status` (JSON), `GET /log`, `GET /log?since=N` (polling, no streaming), and a minimal `/` page showing both with an auto-refreshing log.
2. **Log ring: 32 KB in PSRAM.**
3. **Always on whenever Wi-Fi is up, LAN trust:** read-only, no password, no toggle.
4. **mDNS: yes** (`<name>.local`), **with a settable device name** stored on the device and set the same way as the Wi-Fi settings (protocol request + CLI). Presumably the same name serves as the DHCP hostname; default stays `controlblock-xxxxxx`.
