# Project reorg: cli, examples, tools

Status: Complete

## Description
Reorganise the user-facing and development tooling so each top-level folder has one purpose:

- **`tools/`** is reserved for things used to develop or build this project (e.g. `test-icons`, `pad-sim`, the bake's code generators `gen-types.js` / `gen-hid-keys.js` if they stay dev-only).
- **One JS library** (top level, user facing, lower level than the CLI): the host library (`host/`: USB device API) and the bake functionality (`tools/bake/src`: config baking) merge into a single package. Folder name proposed: keep `host/` (package already `@toptensoftware/controlblock`); see *Flagged assumptions*.
- **`cli/`** (new, top level): a single user-facing `cli/cli.js` covering what the bake CLI (`tools/bake/cli.js`: bake a config, `--upload`) and the Wi-Fi setup script (`host/demo/wifi.js`) do now. It is **only a thin CLI wrapper**: argument parsing and output; all functionality (baking, upload, Wi-Fi credentials) lives in the library. Gets its own folder and documentation (README, and a mention in CLAUDE.md / docs).
- **`examples/`** (new, top level): the test configs (`tools/bake/examples/*`: `net-test.json`, `activity-test.mjs`, `script-test.mjs`, `test-common.mjs`, `upload-test.json`) and the test server (`tools/test-server/`: `net_test_server.py`, `takeover.mjs`). Used for hardware testing during development and by users experimenting.

Everything that references the old paths (CLAUDE.md, docs, wip docs, package.json scripts, tests, `.npmrc`/`file:` deps, relative imports in the examples) must follow the move.

#### 2. Logic in the scripts beyond arg parsing (what moves into the library)
**`tools/bake/cli.js`** (60 lines):
- `loadConfig(file)`: `.json` -> `JSON.parse(readFileSync)`, otherwise dynamic `import(pathToFileURL(path.resolve(file)))` `.default`. -> library.
- Bake a file: `createNodeHost(dirname(resolve(input)))`, `bake(config, host, createRenderer())`. -> library.
- Default output path: `<input dir>/<input basename>.bin` unless `--upload` without `-o`. -> CLI policy (keep in cli, or a tiny library helper `defaultBlobPath(file)`).
- Write blob + print `<out>: N bytes`; print warnings via `formatEntries`. -> CLI (output), `formatEntries` stays a library export.
- `--header`: writes `headerText()` (binpack `formatTypes()`, no banner). Duplicates `gen-types.js` (which adds a banner). See flagged assumption on dropping it.
- `.bin` input: read the file and upload. -> CLI calls a library upload function.
- Error handling: `BakeError` -> its message, otherwise `error: <msg>`, exit 1. -> CLI.
- `src/args.js` (pure, tested in `upload.test.js` "args:" tests x4) is CLI-only -> moves to `cli/`.
- `src/upload.js` `uploadBlob(blob, { serial, force, log, open, reconnect })`: open, uploadConfig with 10% progress log lines, skip-if-same message, reconnect, verify same serial + configSize/configCrc, close. It is library logic with CLI-ish log text. Keep in the library (it's the "upload and verify" flow every client wants), but prefer structured progress over pre-formatted text: e.g. `onProgress(sent,total)` / `onEvent({type:"device"|"progress"|"skipped"|"restarting"|"verified", ...})` and let the CLI format lines; or keep `log` as is (simplest, tests already assert on it). Decide in Plan.

**`host/demo/wifi.js`** (89 lines):
- `show(st)` formats a status (stateName, ip, rssi, reason when RETRYING, MAC unless NO_CREDENTIALS). -> CLI formatting (or a library `formatWifiStatus(st)` if a web UI wants the same text; recommend CLI).
- `waitConnected(cb, seconds)`: polls `wifiStatus()` every 500 ms until CONNECTED (true) / NO_CREDENTIALS or deadline (false), printing each change. -> library, e.g. `cb.waitWifiConnected({ timeoutMs = 30000, intervalMs = 500, onStatus })` on `ControlBlock` (browser safe; could use the `wifiState` event instead of polling, but polling is what's proven).
- Commands `set` (setWifi + wait 30 s, exit 1 if not connected), `get`, `clear`, `status`, `wait [s]`; exit codes 0/1/2. -> CLI. Note it has no `--serial` today; the CLI should add it (`ControlBlock.open({ serial })`).

**`tools/test-server/takeover.mjs`**: open, `takeControl()`, sleep, `releaseControl()`, close. No logic worth a library function (all library calls). Either stays an example script, or becomes a CLI command (`control take|release`, `control hold <s>`). See flagged assumptions.

#### 3. Browser compatibility and entry points
- Browser-safe now: `protocol.js`, `ControlBlock.js`, `Emitter.js`; `lua.js` (wasmoon runs in browsers).
- Node only: `images.js` (sharp, node:zlib), `render-node.js` (node-buttonImage -> canvas native + sharp), `host-node.js` (fs, path, `import.meta.resolve` of node-buttonImage), `upload.js` (only because default `open` is `ControlBlock.open` -> `usb`; otherwise fine), `cli.js`, gen scripts.
- "Browser-intended" but not clean: `bake.js`/`resolve.js`/`ops.js`/`check.js`/`render.js`/`pack.js` use the Node **`Buffer` global** (`check.js:7`, `ops.js:27,83,114`, `pack.js:19,30`, `render.js:34-35`); binpack itself uses its own `buf.js` shim. So the bake core is not browser-loadable yet (PLAN.md lists "browser renderer" as later). Don't fix in this job; record as future work.
- Proposed layout: `host/src/device/` (ControlBlock, protocol, Emitter, images), `host/src/bake/` (all of `tools/bake/src` except `args.js`), or keep `host/src/` flat for the device files and add `host/src/bake/` only (less churn: device imports and README paths unchanged). Recommend the latter.
- Proposed entry points (package.json `exports`):
  - `"."`: `{ "browser": "./browser.js", "default": "./index.js" }` - `index.js` = everything (as today plus bake + Node helpers; existing demo/README imports keep working); `browser.js` = protocol + ControlBlock + Emitter only.
  - optionally `"./bake"` (bake core, for a future web front end once `Buffer` is shimmed) and `"./package.json"`.
  - Keep `main: index.js` too. Relative-path consumers (cli/, examples) import `../host/index.js` directly, so `exports` matters only for package-name imports and bundlers.
- **DRY: duplicates to unify**
  1. `images.js` `encodeImage` and `render-node.js` `createRenderer` both call `packRle({data, info:{width,height,channels:4}}, {})` -> render-node should use `encodeImage`.
  2. `images.js` `imageId` uses `zlib.crc32`; `protocol.js` has `crc32` (same algorithm). -> `imageId` should use `protocol.crc32` (removes a node:zlib import).
  3. ButtonImage(def).render(size,size,4) -> rle565: in `render-node.js`, `demo/demo.js` `iconImage` (+ `keyImage`), and `tools/test-icons/gen.js`. -> one library helper (e.g. `renderButtonImage(def, size) -> rgba` or `buttonKeyImage(def, size) -> {id,data}`); demo uses it (then demo needs no direct node-buttonImage import, which helps moving it to examples). test-icons is a separate dev package with its own deps: leave it (optional).
  4. Two copies of the shared `file:` deps (node-buttonImage, rle565, sharp) in `host/node_modules` and `tools/bake/node_modules` -> one after the merge (tools/test-icons keeps its own).
  5. `--header` (cli) vs `gen-types.js`: same text, banner differs.
  6. `KEY_SIZE` (bake consts) vs `info.keyWidth` (device): different roles (offline bake vs live device); fine.

- `install-links=true` makes npm **copy** `file:` deps into `node_modules` (why edits to node-buttonImage/rle565 need a version bump + reinstall). Likely chosen so node-buttonImage/rle565 resolve their own deps (canvas, sharp) inside the consumer's tree with a single sharp.
- If `cli/` depended on the library with `file:../host` under `install-links=true`, the library would be copied and go stale on every edit, **and break**: `host/src/bake/*` reach `binpack` through `../../../binpack/` relative paths, which point nowhere from inside `cli/node_modules/...`.
- Options for cli/ (and examples/): (1) relative import `../host/index.js` - no install in cli/, never stale, the library's bare imports resolve from `host/node_modules` (Node resolves from the file's real location); (2) `file:../host` with `install-links=false` in `cli/.npmrc` -> npm makes a junction/symlink; Node uses the real path, so also never stale, but needs `npm install` in cli/; (3) npm workspaces with a root `package.json` - bigger change, would hoist deps and interact with the existing `install-links=true`. **Recommend (1)** for cli/ and examples/; cli/ still gets a `package.json` (`type: module`, `bin`, `test` script, no dependencies).
- Consider making binpack a real dependency of the library (`"@toptensoftware/binpack": "file:../binpack"`) so the library is self-contained. With `install-links=true` that copies binpack (edits need reinstall, like node-buttonImage); keeping the relative import keeps binpack edits live. Recommend keeping the relative import for now (the library is private and never copied if consumers import it relatively); note the trade-off in the README.
