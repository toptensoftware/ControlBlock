# On-device render feasibility

Status: Complete (awaiting the user before renaming to complete-)

## Description

Evaluate, by experiment, whether the device can render key images itself. The renderer would compose layers (a baked face or image, text, recolour, a value fill for sliders and toggles) with rle565's renderer. It would encode the result to an opaque rle565 image with rle565's new C encoder and hand it to the compositor like any other key image.

This job is **feasibility only**. Its output is measurements and a recommendation, not a shipped feature. Any experiment code is throwaway or behind a build switch; a later job designs and builds the real thing.

Why: standalone mode can only show pre-rendered key images (no text overlay, no colour change). v0.2's control types (toggle, slider, encoder-style track pad), Lua-set key looks, outside state and the on-screen keyboard all need key looks that change on the device. Control state is the first v0.2 design job, and how state is drawn depends on this.

Questions to answer:
- **Speed:** render + encode time for a 1U (144x144), 2U (288x144) and the largest image (720x432), in release and `-Og`, with typical layers (face + text, face + recolour, slider fill). How long from a state change until the key is on screen?
- **Memory:** internal scratch needed (whole image or banded), PSRAM for the output, and encoder working memory. What does it cost internal RAM?
- **Display safety:** the result must reach PSRAM within the bounce fill rules (fill-gap writes, ~1 KB chunks, no `heap_caps_realloc` growth). Does rendering on core 0 or 1 disturb fills (stress run: `end max`, `missed`)?
- **Fonts:** size and quality of `.rfnt` fonts in the layout blob; text rendering cost.
- **Integration:** how rendered images enter the image store (device-owned images, beside host uploads and `AddExternal`) and how a key switches to one.
- **Alternatives** if the full render is too slow: e.g. drawing a slider fill or a state overlay straight onto a baked image, or a strip of pre-rendered states from the host.

## Notes

User guidance (2026-11-17):
- **RGB565 is enough:** render into a 565 image buffer; no 24/32-bit intermediate is needed. This halves the scratch size, and rle565's renderer already draws into an `IMAGE_BUFFER`.
- **Assets by id:** extend today's images-by-id store into assets by id with a type (rle565, rfnt, svg, ...). Hosted mode would upload fonts and vectors the same way as images, and the layout blob would register them the same way. Evaluate what this means for the image store (`image_store.cpp`), `PUT_IMAGE`/the protocol and the blob; the protocol change itself is for the later design job.
- **On-device SVG would be awesome if possible,** even just rasterised paths (fill, maybe stroke; no full SVG). Evaluate: a minimal path rasteriser (anti-aliased scanline fill, beziers flattened to lines) writing 565 with alpha; code size; speed for an 80 px icon; and which SVG subset the bake would have to reduce icons to (e.g. path-only, pre-transformed, so the device needs no parser for transforms, CSS or groups). Look for small existing libraries (e.g. nanosvg/nanosvgrast: C, no STL, but float-heavy and allocating) against writing our own.

- The `rle565` submodule is pinned at `8da1f8d` (check_image), which looks older than the C encoder: check upstream and update the submodule first.
- The change goes against the current rule "no stock face, tint or font in the firmware" (CLAUDE.md, Screen and Keys). If feasible, that rule changes in the later design job.
- Related ideas: control types, static full-screen images, outside state, on-screen keyboard, MIDI. The user wants no full-screen indicator while ops run.

### Investigation findings (2026-11-17)

Throwaway scripts used (gitignored, run from the repo root): `scratch/svg-survey.mjs` (built-in icon survey + Path2D flatten), `scratch/rfnt-sizes.mjs` (packed font sizes), `scratch/palette-survey.mjs <blob...>` (palette sizes of baked key images), `scratch/map-sizes.mjs <map> <obj...>` (code size per object from a link map).

**1. rle565 C encoder (upstream).**
- Upstream `origin/main` is 2 commits past the pin `8da1f8d`: `a798f5f` "Add C RLE565 encoder" and `f20a3aa` (CLAUDE.md/README only). Fetched only; the submodule pointer was **not** moved.
- The change is purely additive: new `src/rle565enc.c` (467 lines), new declarations in `src/rle565.h` (after `decode_image_argb8888`), tests in `rle565/test/main.cpp`, docs. `src/rle565.c` and `rle565.core.h` are untouched, nothing renamed: **no API break** for `firmware/main` or the encoder/host side. Updating needs `rle565enc.c` added to `firmware/main/CMakeLists.txt` (the source list near line 82, beside `${RLE565_DIR}/rle565.c`) and `firmware/test/test.mk.js` (`otherSourceFiles`), only where encoding is used ("leave that file out of builds that don't encode").
- API (`rle565.h` upstream): `size_t encode_image_rgb565(const uint16_t* px, w, h, stride, void* workspace, size_t ws_size, void* out, size_t out_size)` (and `encode_image_argb8888(..., premultiplied, ...)`). `out == NULL` returns the exact size (a full dry run); returns 0 on failure (bad args, too many colours, out too small). Output matches the JS encoder byte for byte.
- **Memory:** no heap allocation. Caller workspace `IMAGE_ENCODE_WORKSPACE_SIZE(max_colors)` = 14 B per distinct colour (entries 8 B + perm 2 B + hash 4 B), 4-byte aligned, max 65535 colours (so an image using all 65536 RGB565 values can't be encoded at all). Stack use is small (a few structs).
- **Opaque:** the RGB565 path keys every pixel `0xFF00xxxx`, so output is always fully opaque, `firstRow = 0`, `rowCount = h` (no trimming possible: no transparent key), which is exactly what `opaque_image_fits()` (`firmware/main/opaque_row.cpp:55`) requires. >256 colours sets `DRAW_FLAGS_LARGE_PALETTE` (varlen indices); `opaque_draw_rows` handles it (`opaque_row.cpp:69`, per-pixel `read_varlen` path: slower).
- **Not streaming:** needs the whole source image in memory. Passes over the source: trim scan (cheap for 565: first run is non-zero), palette count over every row, rank (heapsort), then per row `encode_row` twice (count runs, then write) plus `row_capture_size`, and short-run groups re-read keys. Palette precedes the rows in the output and its order depends on whole-image counts, so a banded encode would need either an upstream API change (count pass over bands, then encode pass over bands) or rendering every band twice. Integer only, no float. Output written byte by byte (unaligned-safe, not fast).
- **Code size:** not measured (no build of it); by line count expect ~2-3 KB of Xtensa text. Current `rle565.c` is ~23 KB text in the release build (`firmware/build/release/controlblock.map`), ~17 KB in debug.
- Avoiding the dry-run pass: encode straight into a worst-case-sized internal output buffer and then `ImageStore::Put` it (bound for an opaque w×h image with ≤256 colours ≈ 40 + 8h + 4·colours + h·(w + a few varlen bytes)).

**2. rle565 renderer (`rle565/src/rle565.h`, pinned).**
- Ops: `draw_image(IMAGE_BUFFER*, image, dest_x, dest_y, src_x, src_y, w, h, cap, alpha, palette)` (alpha pixels, overall `alpha` fade, palette override, optional capture/`restore_image`); `fill_rect(buf, x, y, w, h, color565)`; `draw_alpha_mask(buf, x, y, mask, stride, w, h, color565, alpha)` (8-bit coverage, blended at 33 levels); fonts: `draw_text`, `draw_glyph`, `font_measure_text`, `font_get_advance`/kerning, `check_font`; palette tools: `normalize_palette`, `prepare_palette`, `recolor_palette(pal, colorA, colorB, channelShift)` (interpolates on one channel: the recolour primitive); `check_image`, `decode_image_argb8888`. Everything clips to the buffer; no float in `rle565.c` (grep).
- `IMAGE_BUFFER` = `{ IMAGE base; uint16_t* buffer; uint32_t stride; void* user; }`; `init_image_buffer(buf, w, h, mem, stride)`, `clip_image_buffer(buf, underlying, x, y, w, h)` (a clipped sub-view).
- **Banding works today:** render into a band-high buffer and shift every draw up by `y0`; clipping does the rest. Precedent: `status_bar_render_rows()` (`firmware/main/status_bar.cpp:74`) draws rows y0..y0+rows of the bar into a `SCREEN_W × rows` buffer this way, and `TestStatusBar.cpp` checks band output equals the whole render byte for byte.
- **Fonts (.rfnt):** one font at one pixel size, pre-rasterised 8-bit coverage bitmaps, optional subpixel (1/2/4/8 bitmaps per glyph), kerning, hash lookup. Packed by `rle565/encoder/font.js` `packFont(file, { size, subpixel, charset })` (fontkit + its own exact-area rasteriser, no hinting). The firmware already uses one: status bar Inter SemiBold 20 px, subpixel 4, ASCII, in `firmware/assets/ui.bin` (`tools/test-icons/gen.js:217`).
- Measured `.rfnt` sizes (`scratch/rfnt-sizes.mjs`):

  | Font, charset, subpixel | 16 px | 20 px | 27 px | 36 px |
  |---|---|---|---|---|
  | Inter SemiBold, ASCII, 1 | 15 KB | 20 KB | 30 KB | 48 KB |
  | Inter SemiBold, ASCII, 4 | 46 KB | 65 KB | 107 KB | 179 KB |
  | Inter SemiBold, Latin-1, 1 | 39 KB | 49 KB | 72 KB | 111 KB |
  | Arial Bold, ASCII, 1 | 12 KB | 17 KB | 27 KB | 44 KB |
  | Arial Bold, ASCII, 4 | 42 KB | 61 KB | 102 KB | 172 KB |

  Default key labels (`host/src/bake/look.js:202`): `bold 15px` (label only) / `bold 11px` (with an icon) on a 72-virtual-px face drawn at 128 px, i.e. **~27 px and ~20 px**, from a system `sans-serif` (Skia). So one label size costs ~20-30 KB (ASCII, no subpixel) to ~65-107 KB (subpixel 4) each, per size. Latin-1 roughly doubles to triples it (Inter's kerning). Per-size bitmaps scale with size², so many sizes add up fast.
- **The encoder package already contains a vector rasteriser:** `font.js` `flattenPath` (quads/cubics flattened to lines by a deviation tolerance, ≤64 segments) and `accumulateLine` + `rasterizeGlyph` (lines ~95-258): exact signed-area accumulation (font-rs / stb_truetype v2 style), prefix sum, `min(1, |sum|)` (non-zero for typical glyphs, no even-odd). It's ~150 lines and ports directly to C (see 5).

**3. The pipeline a rendered image must plug into.**
- `ImageStore` (`firmware/main/image_store.h/.cpp`): `ImageData` header + rle565 in one 16-byte-aligned PSRAM allocation; `ImageEntry { id, data, pixels, opaque, width, height, external, key_refs, live }`. Kinds today: host uploads (`PutBegin/PutData/PutEnd`), **`Put(id, data, size)` "a whole image from memory in one chunk (the device's own images)"** (`image_store.h`, `.cpp:169`; used by `model_put_image`, `model.cpp:104`, and the stress run's replaces), and `AddExternal` (blob images used in place; one contiguous external region; `PixelsRetired` treats that region as never retired). Every finished image is validated by `check_image` (+ opaque required, `model.cpp`: `Init(..., KEY_GRID_W, KEY_GRID_H, true)`), timed in `checks`/`check_cycles`.
- **Replace in place** under the same ID: allocate new, check, install; `ImageStoreListener::OnImageReplaced` (implemented by `KeyLayout`) switches every key using it, old pixels retired and freed after a compositor sweep (`Retire`, `Collect`). This already is "how a key switches to a rendered image": render → `model_put_image(id, ...)` under the model lock → the key redraws. A replace needs room for both copies until the sweep; each state change is a fresh PSRAM allocation (fragmentation to watch).
- **ID spaces:** host IDs are host-chosen (CRC-32 suggested). Blob images get the blob offset as their ID (`layout_apply.cpp:26`, `AddExternal(im->offset, ...)`), so < 4 MB. Hosted and standalone are exclusive (reset between), so device-rendered images need a reserved range per mode (e.g. high bit) or must coexist with the blob's offsets.
- `KeyLayout` (`key_layout.h:31`): `KeyDef { id, page, rect, flags, normal, pressed }` (image IDs); `SetKeys` checks images are live and exactly the rect's size; `GetPage` hands the compositor pixel rects + pixel pointers.
- **Compositor:** draws with `opaque_draw_rows()` (opaque RLE only; `IMAGE_FORMAT_BUFFER` flat images are not drawn today, though a flat 565 path would be a trivial row memcpy). Keys are drawn into PSRAM page buffers on core 1 in fill gaps, ~1 KB chunks, `COMP_CHUNK_WORST_US` 140 µs (tuned on images ≤ ~460 colours: a large-palette image decodes per pixel through `read_varlen`, which may lengthen chunks).
- **Fill gaps** (`fill_gap.h/.cpp`): the fill ISR (core 0) calls `fill_gap_done()`; up to `FILL_GAP_MAX_CLIENTS` 2 (compositor, status bar) take turns (`GapRotor`), notified with the fill's start time. Adding a third PSRAM writer means raising that limit.
- **Status bar precedent** (`status.cpp`, `status_bar.cpp`): task on core 1, priority 3; renders a band (2-4 rows × 800 px) with rle565 into a small **internal** scratch (`s_scratch`, `SCREEN_W × STATUS_BAR_BAND_ROWS_MAX` px, `status.cpp:181`), reading only; then in a fill gap it was given (and only if `fill_gap_fresh(COMP_GAP_FRESH_US)`) memcpys the band into the PSRAM bar; swaps after the last band.
- **But host uploads are not gap-gated:** `PutData` memcpys into PSRAM from the protocol task (core 0) at USB speed, and the stress run's "image replaces" cases (~1 MB/s, `main.cpp:441`, `STRESS_REPLACE`) and the Lua heap churn (core 0, PSRAM) pass. So writing a ~4 KB encoded result to PSRAM from a core 0 task is the same load as an upload. Rendering *into PSRAM scratch* (tens to hundreds of KB per image) is a new load and would need its own stress case. Tasks: protocol and op tasks on core 0; compositor (prio 4), swipe (10), touch (5), status (3) on core 1; the fill ISR on core 0 (`docs/page-compositor.md:306-314`).
- **Internal RAM** (CLAUDE.md, Open Items): release with Wi-Fi connected ~106 KB free, **largest block 64 KB**, plus ~29 KB (render cell gone) and ~12 KB (op stack to PSRAM) expected since: ~140-150 KB free (to be re-read). A whole 1U 565 scratch is 144×144×2 = 41.5 KB (fits one block); 2U 288×144 = 83 KB (over the largest block: needs banding or PSRAM); 720×432 = 622 KB (PSRAM or bands). Encoder workspace for 1024 colours = 14 KB.

**4. Assets by id: touch points (mapping only).**
- Protocol: `PUT_IMAGE` (`0x10`), `FREE_IMAGES` (`0x11`), `QUERY_IMAGES` (`0x12`) in `docs/protocol.md:116-300`; `BAD_IMAGE` (error 5) defined as rle565/opaque failure (`protocol.md:96`); the opaque check is in the spec text (`protocol.md:275`). A type needs a field (new request or a typed variant; payloads may only grow at the end) and `GET_INFO` limits. Firmware: `protocol.cpp/.h` (parser, `ProtocolHost`), `TestProtocol.cpp`.
- `ImageStore`: validation is rle565-only (`CheckPixels`: `check_image_header`, `check_image`, max size, opaque); `ImageEntry.width/height/opaque` are image facts. A typed asset needs a per-type check (`check_font` exists in rle565; an SVG/path format needs its own) and the opaque/size rules only for key images. `require_opaque` would become per-type. `PixelsRetired`/`IsRetired` and the compositor only care about images; non-image assets are read by the renderer (needs its own refs or the model lock while rendering).
- `KeyLayout::SetKeys` checks "images live and exactly the rect's size": must still refuse non-image assets as key images.
- Blob: `host/src/bake/schema.js` `key` has `normal`/`pressed` as inline byte arrays (`bytes(...)`), not IDs; the loader (`layout_blob.cpp`, `layout_apply.cpp`) dedupes by offset. Typed assets would need a blob asset table (or typed byte fields), regenerate `layout_types.gen.h` (`tools/codegen/gen-types.js`), bump `LAYOUT_BLOB_VERSION`, re-bake `firmware/test/data/sample_layout.bin`.
- Host library: `host/src/ControlBlock.js` (`putImage`/query/free, `imageId` CRC in `host/src/images.js:20`), `docs/guide/hosted-mode.md`, `test/FakeDevice.js`; the bake (`host/src/bake/look.js`, `render.js`, `pack.js`).

**5. SVG on device.**
- **Icons in use:** button-face's 42 built-ins (`node_modules/@toptensoftware/button-face/src/icons.js`) and Material Symbols downloads (`material.js`: `@name?style,fill,weight,grade,size`, SVGs from Google, single `<path>` in a `viewBox`). Survey (`scratch/svg-survey.mjs`): 1038 path commands / 26 KB of path text in all; ~24 are Material-style single `<path fill=currentColor>`; the rest are Inkscape files with `<g transform>`, `style=` attributes, 4 stroked arrows (2-command strokes), `<rect>` (cancel), even-odd (playstation), and **gradients** in apple-tv and steam. Commands used: M/L/H/V/Q/T/C/S/A/Z, relative and absolute.
- **The bake can reduce them with what's installed:** `@napi-rs/canvas` `Path2D` (`node_modules/@napi-rs/canvas/index.d.ts:634-689`) parses an SVG `d` string, and has `transform(matrix)`, `stroke(options)` (stroke to fill outline), `asWinding()` (even-odd to non-zero), `simplify()`, `op()` (union), `toSVGString()`. A round trip of every built-in's `d` data (asWinding + simplify) worked for all 42 and output only absolute **M, L, Q, C, Z** (Skia turns arcs into conics/quads): 0.1-9.7 KB of text per icon, median ~0.7 KB, as binary floats/int16 roughly half that. Missing: no SVG document parser in the deps (no XML lib), so `<g transform>`, `<rect>/<circle>`, `style=` and stroke attributes need a small walker in the bake (or reject non-path icons); gradients can't be reduced to a single fill (fall back to a host-rendered image).
- **Device subset suggestion for the Plan:** per icon, a list of (colour or "currentColor", non-zero fill path in absolute M/L/Q/C/Z, already in the icon's pixel or a fixed unit space); no parser, transforms, CSS, groups, strokes or gradients on the device.
- **Libraries (from knowledge, not measured here; see Flagged assumptions):**
  - *nanosvg + nanosvgrast* (Mikko Mononen, zlib): single headers, C, no STL. Parser: `malloc`/`realloc` for shapes and points, float, own `atof`; converts everything (shapes, arcs, transforms) to cubic beziers. Rasteriser: float flattening, `realloc`-grown edge/point arrays, scanline with 5 vertical subsamples (`NSVG__SUBSAMPLES`) and fixed-point horizontal coverage, RGBA8888 output only (we'd need a 565 blend or a coverage-only variant). Strokes, gradients, even-odd supported. Est. 20-35 KB code. Its `realloc` growth must not use `heap_caps_realloc` on PSRAM (bounce fill rule): give it internal RAM or an alloc-copy-free shim like `LuaHeapAlloc`.
  - *PlutoVG* (MIT, C): FreeType-derived exact-area gray rasteriser, strokes, dashes, gradients, transforms; ARGB32 premultiplied canvas only (4 B/px scratch), `malloc` throughout; est. 60-120 KB code. Higher quality, but heavy and 32-bit.
  - *ThorVG*: C++ (own containers, but `new`, virtuals, a large engine); LVGL v9 bundles it; est. ≥150 KB code even trimmed. **Too big / wrong shape**, confirmed as expected.
  - *stb_truetype*'s v2 rasteriser: the same signed-area algorithm as `font.js`, with `STBTT_malloc`; liftable but tied to its glyph shapes.
  - **Own rasteriser** (port of `font.js` `flattenPath` + `accumulateLine`): ~150-200 lines C, float (the S3 has a single-precision FPU; avoid doubles, divisions per segment only), output **8-bit coverage** straight into `draw_alpha_mask` in any colour (recolour for free). Accumulator `(w+2) × h` floats: an 80 px icon is 26 KB, or band it (`accumulateLine` already clips to `[0, height)`, so a band is a y offset plus clipping) or use int32 fixed point. Same algorithm as the font packer, so the host can produce reference masks for tests. Non-zero only (bake uses `asWinding()`).
- Same rasteriser could also rasterise font glyphs on the device from outlines (any size from one outline font) instead of per-size `.rfnt` bitmaps: an option for the font-size problem in 2, not needed for the first experiment.

**7. Risks and blockers (none blocking the experiments).**
- **Colour count:** the encoder's workspace and the decode path depend on distinct colours. Host-baked opaque keys today (`scratch/palette-survey.mjs`): urem2 144×144 median 56 colours, max 325 (2 of 124 large-palette); sample layout max 253; `test_keys.bin` 1U max 460. AA text (33 blend levels) over a shaded face multiplies colours (up to ~33 × face colours), so device renders may cross 256 more often: bigger output, the slower large-palette decode in `opaque_draw_rows`, and chunk timing to recheck. >65535 colours can't encode at all (a photo-like 720×432 could hit it): need a fallback (e.g. quantise, or a flat 565 image).
- **Whole-image encode vs internal RAM:** 1U fits internal (41.5 KB scratch + ~14 KB workspace); 2U and larger need PSRAM scratch (a new heavy PSRAM writer: stress run) or banded render-twice/an encoder API change.
- **Fonts:** the "no stock face, tint or font in the firmware" rule (CLAUDE.md, Screen and Keys) is for keys; fonts would come from the blob/host as assets, so no conflict for the experiment. Size per font size (table above) and PSRAM: the blob stays resident (urem2 ~440 KB), image store = free PSRAM − 512 KB.
- **Code size:** app is 1.24 MB release / 1.32 MB debug (`firmware/build/*/controlblock.bin`, 2026-11-15) in a 2 MB partition: ~0.7 MB headroom. Encoder ~2-3 KB, own rasteriser a few KB; nanosvg tens of KB; PlutoVG/ThorVG eat a large share.
- **`-Og` speed:** `draw_image`/`draw_alpha_mask`/encoder loops are untested under `-Og` on the device (the `fill_px` lesson: a naive 16-bit loop cost ~350 µs); measure both presets.
- **Allocator rules:** never grow PSRAM blocks with `heap_caps_realloc` (bounce fill rules); third-party libraries that `realloc` need a shim.
- **Lock time:** `model_put_image` holds the model lock for allocate + memcpy + `check_image`; rendering itself must happen outside the lock (the touch router and compositor take it).

**Cheaper alternatives spotted (for the Plan's comparison).**
- *Palette recolour without encoding:* a key image's colours live in its palette (`opaque_draw_rows` maps indices through it), so a recoloured copy of a baked image is a memcpy of ~3-5 KB plus rewriting palette entries (`recolor_palette`-style), then `Put`: no render, no encode.
- *Flat 565 images:* skip the encoder by storing `IMAGE_FORMAT_BUFFER`-style raw 565 (41.5 KB per 1U in PSRAM, ~10x an RLE key) with a row-memcpy path in the compositor; trades PSRAM for encode time.
- *Host strip of states* and *drawing a fill/overlay onto a baked image's 565 decode* remain as in the Description.

### What the numbers say

1. **The encoder is the cost, not the render.** For a 1U, the render takes ~0.7-1.1 ms (release) but the encode ~13-14.8 ms: **~17× the render** on the device, against ~7× on x86. That's ~630 ns (~150 cycles) a pixel. Why (from `rle565/src/rle565enc.c`):
   - Every pixel is read about six times: the trim scan (`row_has_pixels`), the palette count (`next_run`), `encode_row` twice per row (count the runs, then write them), `row_capture_size`, and `put_group` re-reads literal runs. Our `count_colors` adds a seventh pass.
   - Every read goes through `source_key()`, which branches on the source format per pixel.
   - Every literal pixel's palette index is a hash lookup (`palette_index` → `palette_slot`, a 64-bit multiply plus probing).
   - Output goes byte by byte through a bounds-checked sink (`put_u8_at`).
   - x86 hides most of this (out-of-order, big caches); the in-order Xtensa doesn't.
   
   **Estimate:** an RGB565-only fast path is likely 3-5× faster, i.e. ~3-4 ms a 1U. It would walk each row once into a run list, map runs to indices through a 64K-entry direct table instead of the hash, and write the output with a plain pointer. The table is 64 KB of u16; it could be a 2-level or PSRAM table, or a 256-entry cache in front of the hash. This is an estimate, not measured. It needs an upstream rle565 change, and the JS byte-for-byte parity test (`TestRleEncode.cpp`) guards it.

2. **State change to screen: ~33-41 ms for a 1U, ~55-78 ms for a 2U (2-4 frames at ~49 fps).**
   - That's render+encode ~14-16 ms, put ~2.5 ms, then 10-25 ms until the compositor has drawn it and the fill shows it (frame phase plus a 1U draw of ~3 ms).
   - Fine for toggles, state from outside, Lua key updates and the on-screen keyboard's text field.
   - Too slow for a slider following a finger (one update every 2-3 frames). The recolour copy shows the floor without encoding: **13-17 ms** (0.1 ms copy + 2.3 ms put + the draw).
   - A smooth slider wants a cheaper path: the faster encoder, a value-only overlay (e.g. draw the fill straight into the encoded image's runs, or into a key-sized raw 565 image), or simply redraw at a lower rate while dragging.

3. **Put costs ~2.3-2.9 ms (1U), 4.7 ms (2U), 27.6 ms (720×432), all under the model lock.**
   - It scales with the image's pixel count, not its bytes (11 KB for 720×432 took 27.6 ms). `ImageStore::Put` runs `check_image` (rle565 `walk_image`), which checks the palette index of **every pixel** of the PSRAM copy (~110 ns a pixel). That's on top of the allocate and the memcpy into PSRAM.
   - It matters: the touch router and the compositor wait on that lock. A 2.5 ms hold per 1U is tolerable; 28 ms isn't.
   - Fix for images the device made itself: they're the encoder's own output, so skip `check_image` (a trusted put), or check the internal-RAM output before taking the lock. Either takes the put down to the copy (~tens of µs for 4 KB).
   - Host uploads keep the check: `PUT_IMAGE` streams outside the lock already, but layouts with many images could take the same lock-free check.

4. **Display safety: the render's picture buffer must not be in PSRAM.**
   - Every case with its buffers in internal RAM passed in both builds: 0 missed, end max ≤ 244 µs, chunk max ≤ 131/140, 0 late gaps.
   - Every case that rendered into a PSRAM picture missed fills in release: 2U 1-2 missed (end max 622-637 µs, one compositor chunk 148/140), 720×432 18 missed.
   - Debug passed all of them only because its slower render writes PSRAM less often. So the render's 565 picture is a new heavy PSRAM writer on core 0, exactly what the bounce fill rules warn about.
   - The >256-colour image decodes fine in the compositor (chunk max 105/131 µs, 0 late), though with less margin in debug.
   - **Rule: render scratch lives in internal RAM, in bands.** The encoder needs the whole image, so 2U and bigger can't be encoded today without a PSRAM picture. Options:
     - (a) An upstream **two-pass banded encode API**: pass 1 counts colours band by band, pass 2 encodes band by band, rendering each band twice. The render is cheap: ~1 ms a 1U, so ~2× render. Keeps the format. Recommended.
     - (b) **Gap-paced PSRAM scratch:** write the picture through `fill_gap` like the status bar. This slows renders to the gaps' bandwidth and adds a new gap client.
     - (c) **Store something simpler** than rle565 for device-made images: raw 565 (41 KB a 1U, 10× the RLE) or a trivially banded RLE. It needs a second draw path in the compositor and costs PSRAM.
   - 1U pictures fit internal RAM whole (40.5 KB) and passed, but a 40.5 KB block plus 8 KB workspace plus 22 KB worst-case output is ~71 KB of internal RAM at once: too much to keep for a running device (min ever free was 71-84 KB in the stress + lab runs). Banding (a) brings it to ~4.5 KB of band + 8 KB workspace + an output buffer, or write the output straight to its PSRAM slot in ~1 KB gap-sized pieces.

5. **Recolour copy: 0.07-0.1 ms + put.** This is the fast path for colour-only state (toggle on/off tint, a "busy" colour), ~500× cheaper than render + encode; with a trusted put it's well under a millisecond.

6. **Path rasteriser: feasible.** An 80 px icon from paths costs ~1.5 ms more render than the baked rle565 icon in release (2.25 vs 1.08 ms for the whole key; ~1.8 ms in debug), and it matches the JS reference within 1 level. Scratch is float: 31 KB whole or 6.2 KB in 16-row bands (use bands). Text from glyph outlines costs ~1.3 ms more than an `.rfnt` label and looked the same by eye.

7. **Memory and code.**
   - **Internal RAM:** the lab ran with 147-201 KB free at boot. In the stress + lab runs the minimum ever free was 71-84 KB, and the largest block dropped to 72 KB once Wi-Fi-sized allocations happened. The lab task used ~2.1 KB of its 8 KB stack.
   - **PSRAM:** a 1U image is 3.3-5 KB, and 10 rendered keys used 53 KB of the image store.
   - **Code:** the parts a real renderer keeps are ~7 KB of release code (encoder 3.3 KB, path rasteriser 2.5 KB, layer render 1.1 KB).
   - **Fonts** (Inter, ASCII, step 4): 20 KB at 20 px, 31 KB at 27 px; subpixel 4 is ~3.6× bigger (110 KB at 27 px) and looked no different on a key. Latin-1 is 2-3× ASCII.

### Verdict

**Feasible, with constraints.**
- **What works:** an on-device renderer for key looks (text over a face, recolour, value fills, simple vector icons) works on this hardware. It costs ~7 KB of code and a few KB of PSRAM per key, and shows a 1U state change in ~35-40 ms today.
- **Constraint 1, internal RAM only:** renders must keep their pixels in internal RAM, in bands. A PSRAM picture missed fills.
- **Constraint 2, encoder speed:** the encoder needs speeding up (and a banded API) before sliders or larger keys feel live.
- **Constraint 3, no check under the lock:** device-made images must not be re-checked under the model lock.

### Recommended architecture (for the design job)

- **Assets by id with types** (finding 4): image (rle565), font (`.rfnt`), path (the int16 1/16 px format from step 5), later more. Host uploads (`PUT_IMAGE` grows a type, or a new `PUT_ASSET`) and the layout blob register them the same way. Device-made images get their own ID range (blob images use their offset as ID).
- **Key looks as layer lists** (image, fill, text, path; recolour via palette) stored in the blob per state. A small device "look renderer" turns look + state (+ text from scripts) into one opaque rle565 image, then `Put`s it trusted.
- **Render path:**
  - band into internal RAM (16 rows: ~4.5 KB 565 + path scratch ≤ 6.2 KB);
  - encode with a faster, banded rle565 encoder (upstream work: RGB565 fast path + count/encode in bands);
  - write the output into its PSRAM slot in ≤ 1 KB pieces;
  - trusted put without `check_image`.
  
  Run it on a core 0 task (like the op task), one render at a time, coalescing state changes per key (latest wins) so a burst never queues up stale renders.
- **Fast paths:**
  - **Recolour copy** for colour-only states.
  - **Host-baked state images** (a strip per state, as today) stay valid for anything the device can't draw well, e.g. photos or gradient logos.
- **Fonts:** `.rfnt` per size in the layout blob (sp1, ASCII by default, Latin-1 opt-in), 1-3 sizes per layout. Glyphs from outlines only if many sizes are needed: it works, but costs ~1.3 ms a label and needs advances and kerning on the device.
- **SVG:** the bake reduces icons to path-only, pre-transformed absolute M/L/Q/C/Z, single-colour fills, in our int16 format. It needs a small SVG walker in the bake for `<g transform>`, `style=` fills and `<rect>`; 21 of 42 built-ins pass today without one. Gradients stay baked rle565 images. No SVG parser and no nanosvg on the device: our rasteriser is ~2.5 KB and exact. The nanosvg facts in Flagged assumptions weren't re-verified because it isn't recommended.
- **Text layers clip to their box** (or measure and shrink), so a label can't leave its face (the wide-key bug).

## Flagged assumptions
- (Step 2) The text layer doesn't clip to its box (only to the image); a long label overflows the box. Clipping would need a clip view built per band (`clip_image_buffer` takes unsigned x/y, so a box above the band needs care). Left for the design job.
- (Step 2) The colour count bitmap shares the encoder workspace, making the minimum workspace 8 KB even for few colours; a cheaper count (e.g. the encoder's own failure as the signal, grown workspace) wasn't tried.
- Library facts for nanosvg/nanosvgrast, PlutoVG and ThorVG (licences, allocation and float behaviour, subsample counts, code-size estimates) are from memory, not checked against current sources or measured; the Plan should verify before choosing (only the own-rasteriser option was traced in code, `rle565/encoder/font.js`).
- Encoder code size (~2-3 KB) and the internal RAM free figure (~140-150 KB, largest block 64 KB) are estimates; the latter is CLAUDE.md's figures plus its expected savings, not a fresh reading.
- Default label pixel sizes (~20 and ~27 px) assume the foreground is drawn at the 128 px face size: button-face scales font px by button size / virtual size (`scale.js`, default 72), so 128/72; not checked against a rendered label.
- Assumed the renderer would run on a core 0 task (like the op task) with internal scratch, writing only its encoded output to PSRAM; core 1 rendering into PSRAM is the case the bounce fill rules warn about.
- (Plan) `rle565enc.c` goes into the firmware only under `CB_RENDER_LAB`, not always: the experiment shouldn't change normal builds (`--gc-sections` would likely drop it anyway; the size is measured in step 8).
- (Plan) Lab-rendered images use IDs from a reserved high range (e.g. `0xFFxx_xxxx`) so they can't collide with blob offsets (< 4 MB) or the stress run's IDs; the real ID scheme is for the design job.
- (Plan) The path test vectors' generator is checked in (`tools/render-lab/`), not left in `scratch/`, because `firmware/test/data/path_vectors.bin` must be reproducible; it can be deleted with the lab later.
- (Plan) Path rasteriser tolerance ±2/255 per pixel against the JS (double) reference; adjust in step 6 if single-precision float needs more, and record why.
- (Step 4) The "shaded alpha face" is a new grey linear-gradient face from the same SVG as `test_keys.bin`'s faces (grey so recolour cases have something neutral to work on); the icon is the existing 80 px `volume-up` render from `tools/test-icons/out/`.
- (Step 5) Icons are fitted by their viewBox (uniform scale, centred) into 80×80, not cropped like `test_keys.bin`'s icons (rendered at 112, centre 80 cropped); so they look smaller than the test keys' icons. Fine for rasteriser vectors.
- (Step 5) The icon filter treats any `style=`, `transform`, `<g>` or non-path element as unsupported rather than writing an SVG walker (the plan said to skip and report them).
- (Step 6) The plan said "caller gives the accumulator and segment scratch"; streaming the segments into the accumulator needs no segment scratch, so there's only the accumulator (the plan's intent: no heap).
- (Step 6) A path layer's scratch is passed to `RenderLabRender` (new defaulted args) rather than held in the layer; a band needs accumulator + mask for its rows of the tallest path box. Rendering with too little scratch draws nothing (all or nothing) rather than skipping the path.
- (Step 6) A path without a leading M starts at (0, 0) and is filled, as the JS does; `PathCheck` doesn't insist on a leading M.
- (Step 7) The device gets the cases' paths by embedding the whole test vector file (190 KB, masks included) under `CB_RENDER_LAB` rather than a paths-only lab asset: no second format, flash is plentiful for a lab build. A real design would ship paths without masks.

- (Step 7) Case choices beyond the plan's list: a 27 px subpixel-4 label case (font question) and an rle565 image icon case (baseline for the path icon). The 2U case is two 128 px faces side by side (no 2U face asset); the 720×432 case is mostly flat fills, so its colour count and size are optimistic for a photo-like full-screen image.

- (Plan) A `RENDER_LAB` boot leaves its sample keys on page 0 instead of the stored layout (lab builds only), for the visual check.
- (Step 8) Buffer placement is decided at run time (internal if ≤ 48 KB and 24 KB stays in the largest internal block, else PSRAM) and logged per case, rather than fixed per case; at boot (before USB/Wi-Fi) internal RAM is plentiful, so 1U cases will likely be all internal, which is the optimistic case for a running device.
